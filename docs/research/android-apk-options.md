# Android APK options for Aporia

Checked 6 October 2026. This compares ways to deliver Aporia on Android; it does not change app code.

## Current app shape

Aporia already has a standalone PWA manifest and a service worker ([`static/manifest.webmanifest`](../../static/manifest.webmanifest), [`src/app.html`](../../src/app.html), [`src/service-worker.ts`](../../src/service-worker.ts)). The service worker caches built/static assets, while leaving navigation, authentication, and API requests network-only, so only cached assets work offline. Aporia is not a static client bundle today: [`vite.config.ts`](../../vite.config.ts) selects `adapter-node` outside Vercel, [`src/routes/+layout.server.ts`](../../src/routes/+layout.server.ts) and [`src/routes/[id]/+page.server.ts`](../../src/routes/%5Bid%5D/+page.server.ts) read data through server modules, and [`src/lib/server/database.ts`](../../src/lib/server/database.ts) opens `better-sqlite3`. The `src/routes/api/` handlers also run on that Node server. There is no `android/` project or `capacitor.config.*` yet. The APK alone therefore would not contain the existing Node server, SQLite database, or uploaded files.

## Options

The packaging difference is where the web UI lives and who renders it. A TWA APK contains the Android launcher/configuration shell; the actual site is fetched from its HTTPS origin and rendered by a compatible browser provider, fullscreen. A Capacitor APK normally copies the compiled frontend bundle from its configured `webDir` into the Android project and displays it in an embedded Android WebView; API/database work can still live on a remote server. ([TWA overview](https://developer.chrome.com/docs/android/trusted-web-activity), [Capacitor sync](https://next.capacitorjs.com/docs/next/getting-started))

A custom Android WebView app uses the same embedded-WebView model as Capacitor but gives you the Android shell and bridge to implement yourself. It can load the current hosted site directly, which preserves Aporia's SSR, but still depends on the Android System WebView and the network. Android supports both remote URLs and packaged local assets in WebView. ([Android WebView](https://developer.android.com/develop/ui/views/layout/webapps/embed-web-content-in-app), [Android local content](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content))

| Approach | Reuses | Advantages | Costs and limits | Fit for Aporia |
|---|---|---|---|---|
| **Trusted Web Activity (TWA) with Bubblewrap** | The deployed PWA, manifest, service worker, and existing Node/SQLite host | Fastest route to a signed Android launcher app; fullscreen browser rendering; website updates can ship without rebuilding the Android shell; very little UI duplication. Bubblewrap reads the web manifest and can build a signed APK. It supports the manifest's `share_target` and generates Android intent filters for it. ([Android TWA guide](https://developer.android.com/develop/ui/views/layout/webapps/guide-trusted-web-activities-version2), [Bubblewrap CLI](https://github.com/GoogleChromeLabs/bubblewrap/blob/main/packages/cli/README.md), [Bubblewrap Android manifest template](https://github.com/GoogleChromeLabs/bubblewrap/blob/main/packages/core/template_project/app/src/main/AndroidManifest.xml)) | The site must be hosted at an origin you control and verified by Digital Asset Links at `/.well-known/assetlinks.json`; the file must match the app id and signing certificate. A verification failure falls back to a browser Custom Tab. TWA content is still delivered by Chrome or another compatible browser provider; the Android host has no direct access to page state, cookies, or `localStorage`. ([TWA overview](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities)) | **Best first APK if the goal is a directly installable package and Chrome-at-runtime is acceptable.** Keeps SSR, API routes, login, SQLite, and uploaded files on the server. It does not make them local or offline. Add and implement `share_target` to receive shared content. |
| **Capacitor (WebView hybrid app)** | Svelte UI and most browser-side editor code, with access to native plugins | Produces a more configurable Android app with a JavaScript-to-Kotlin bridge and room for native capabilities such as share intents, notifications, or file integration. It can package frontend assets locally, so those assets can open without a network. ([Capacitor install guide](https://capacitorjs.com/docs/getting-started), [Capacitor Android guide](https://capacitorjs.com/docs/android), [Android local web content](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content)) | Capacitor expects a built web-assets directory with a root `index.html`. Aporia's server-side layout and page loads call server modules directly, in addition to its API routes; they cannot simply run from a static APK. Its frontend would need a static/client shell and an explicit API origin or proxy, while the Node backend remains reachable remotely or is redesigned. SvelteKit supports an SPA fallback for mobile wrapping, but this is a deployment-mode change. ([SvelteKit static adapter](https://svelte.dev/docs/kit/adapter-static)) Bundled frontend changes require an app update. Aporia also has a service worker; Capacitor's troubleshooting docs flag service workers as a possible cause of native plugin injection problems, so validate the existing worker early. ([Capacitor troubleshooting](https://capacitorjs.com/docs/android/troubleshooting)) | Choose this if native phone features are on the roadmap, or if you want more control than TWA and accept adapting the frontend/backend boundary. It is not a shortcut to a standalone local SQLite app. |
| **Native Android app (Kotlin/Compose)** | Product requirements and backend APIs, but little UI implementation | Most control over Android UI, lifecycle, permissions, and integrations. A native client can use the existing server APIs, or a separate local-data architecture can be designed. | Rebuild and maintain the editor, page navigation, tables, search, import/export, authentication, and mobile interactions in Android. A local-first/offline version also needs a mobile data and synchronization design. These are project-specific estimates based on Aporia's current web implementation. | Reserve this for a strategic Android-first product or requirements that a WebView cannot meet; it is the largest investment. |

## Recommendation for this project

For Aporia's specific requirements—an independently installable APK, a server address the user can change, and appearing in Android's Share menu—the project now uses a **small custom Android WebView host** that loads the existing hosted app. The Node/SQLite backend remains on the configured server. The APK does not bundle the server or the Svelte UI, and it uses Android System WebView to render the site. Shares of text and links are forwarded to the authenticated Aporia server to create a page. This avoids a full native rewrite and does not require Chrome to install or launch Aporia.

Choose **TWA/Bubblewrap** instead when the app should simply open one fixed, verified HTTPS origin and browser-provider rendering is acceptable. Its APK is smaller and the website can update independently, but a TWA is not a browser-free renderer and does not provide the same direct WebView-to-Android bridge for a user-editable server origin. If the only goal is a home-screen icon for one origin, the Chrome-installed PWA already provides that; an APK mainly adds a separately distributed Android package.

For the additional goal of receiving Android shares, add a `share_target` entry to the web manifest, then implement its action route to capture the received title, text, URL, and/or files and offer the intended Aporia action (for example, create a page or insert content). Chrome documents this API for installed web apps, and Bubblewrap currently reads the field and generates the Android intent filter. ([Web Share Target API](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target), [Bubblewrap CLI](https://github.com/GoogleChromeLabs/bubblewrap/blob/main/packages/cli/README.md))

If “without a browser” also means **without Chrome or a browser provider at runtime**, a TWA does not meet that stronger requirement. The smaller alternative to a full native rewrite is a custom Android WebView host that loads the hosted Aporia site and declares Android `ACTION_SEND` intent filters; Android's WebView is a system component, and the wrapper would forward share payloads into a web route. Capacitor can provide the native shell and plugin bridge, but Aporia's current server-side loads still need restructuring before its UI can be packaged as local web assets. ([Android WebView](https://developer.android.com/develop/ui/views/layout/webapps/embed-web-content-in-app), [Android receive shared data](https://developer.android.com/develop/ui/compose/sharing/receive))

Depending on the device and install path, Chrome may already have installed the PWA as a provider-signed **WebAPK**. Chrome creates and updates that package; it is not a developer-controlled APK file you can sign and distribute yourself. ([Chrome for Developers: WebAPK updates](https://developer.chrome.com/blog/webapk-update-frequency))

From a machine with Node.js and Android build tools, the initial Bubblewrap flow is:

```sh
npm install --global @bubblewrap/cli
bubblewrap init --manifest=https://<your-domain>/manifest.webmanifest
bubblewrap build
```

The build produces a signed `app-release-signed.apk` for device installation. Keep the signing key safe and stable: the matching certificate fingerprint is part of Digital Asset Links, and changing it can break TWA verification. ([Android TWA guide](https://developer.android.com/develop/ui/views/layout/webapps/guide-trusted-web-activities-version2))

For direct installation, use the APK. For Google Play distribution, publish an AAB; Play generates optimized installable APKs from it. ([Android App Bundle FAQ](https://developer.android.com/guide/app-bundle/faq))
